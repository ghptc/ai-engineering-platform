# ADR 017 — owner-scoped dependency governance

Status: implemented for public npm, exact versions, with explicit certification limits below.

The static frontend catalog is an offline bootstrap, not a general dependency authorization system. Replacing it with unrestricted installation would violate the executor boundary. Instead, introduce durable versioned dependency requests, separate resolution consent, exact graph approval and an authenticated executor control plane. No application-specific PDF dependency is added to the catalog.

`DependencyApprovalRequest` records project/run/stage/role/task/operation identity, exact direct packages and classification, ecosystem/manager/registry, model justifications/alternatives/risks, evidence/checkpoint references, deadline, status, version, parent request and owner audit. Model text cannot approve a request. `RequestDependencyApproval` is a strict v1 agent tool and a ninth closed Runtime V2 message kind. Pending requests stop the affected run at `AwaitingDependencyApproval`; completed stages, model checkpoints, usage and operation identities remain intact. Identical package requests deduplicate; a changed proposal following Request Changes links to its prior request.

The owner first authorizes bounded public registry metadata/tarball acquisition, then reviews the complete resolved direct/transitive graph and approves packages independently. Partial approvals grant nothing executable until the entire graph is approved. License declarations are registry data, not legal certification; vulnerability status and provenance signatures remain explicitly unverified. The owner explicitly resumes the same execution. Original deadlines, costs, tool limits and iterations are checked; financial extensions use the existing separate owner limit authorization. Rejection/change requests resume only to find an allowed alternative.

Acquisition runs a fixed trusted npm helper under the existing Docker isolation checks: immutable owner-pinned image, non-root, no network, no mounts/credentials, read-only root, dropped capabilities, private IPC/cgroups, bounded tmpfs/PIDs/CPU/memory, timeout and independent cleanup. A framed stdin/stdout protocol brokers HTTPS through the executor to `registry.npmjs.org` only. No redirect, proxy, arbitrary URL/flag, repository .npmrc, script, credential or Git operation is accepted. Package-manager subprocess stdin is isolated from the broker. Bounds: 20 requested roots, 500 resolved entries, 1000 registry reads, 64 MB total responses, 8 MB metadata/20 MB tarball response, 48 MB cache content, at most 120 seconds and 1 GiB, lowered by the original run deadline and daemon profile ceilings. Cleanup failure blocks further executor use.

Native npm resolves semver/peer/transitive relationships; agents do not invent lockfiles. The helper exports only SHA-512 content-addressed tarball blobs, never npm configuration, headers or indexes. Every blob is rehashed and every package integrity must exist in the cache. Canonical package names, aliases/install paths and tarball origins are checked. A SHA-256 plan fingerprint binds source-before hashes, exact manifest/lock, package metadata, cache identity, repository/project/run and resolver image/contract. Project/run/repository grants are private durable executor records, reachable only through the authenticated control interface; ordinary agent tools cannot invoke it. No global catalog is extended.

`PrepareApprovedDependencies` applies only approved frontend manifest/lock bytes, reconciles each file against before/after hashes, preserves intervening edits, invalidates prior test certification and writes normal fenced/idempotent receipts. Workloads receive verified cache files through the bounded stdin archive, never a host mount. Install scripts and network stay disabled. Every governed build checks exact authorized roots and lock bytes. Even before a grant, cached-but-unapproved direct dependencies cannot start a profile; known policy rejection gives structured request guidance instead of granting permissions. Failed tests/integrity checks retain the existing delivery blocks and human PR boundary.

An explicit owner resume may obtain a fresh bounded assessment after a *saved tool-free blocked model proposal*. The prior output and charges are retained and referenced; completed stages and potentially completed mutating operations are never skipped or replayed on that basis. This corrects the older blocked-checkpoint replay trap without manufacturing a dependency list or changing budgets. No existing incident is automatically resumed.

Persistence is additive: `dependency_approvals_v1` contains CAS-versioned aggregates and immutable-in-content audit entries plus bounded list projections. Full lockfiles are fetched only for a selected request; UI renders at most ten request rows and fifteen package rows. Requests, decisions and checkpoints survive process/container recreation when existing Mongo/executor volumes are retained. Registry failure remains a recoverable wait. An explicit retry checks for a completed receipt and an absent old helper before reacquiring source-free artifacts; it never blindly retries a source mutation.

Deploy with the normal `docker compose up -d --build`; no per-package Compose/catalog/lock edit is required. Preserve all Mongo, key/control, executor state and image-pin volumes. Existing runs retain runtime versions, receipts and instruction snapshots; new capability instructions are versioned. Legacy workspaces must match their persisted repository identity even when a project snapshot is unavailable. Rollback requires quiescing active acquisition, retaining records/cache/grants and deploying old images. Keep dependency-waiting runs stopped until code understands the appended enum value; old workers must not reinterpret or migrate them into runnable stages. Never delete receipts/candidates to recover capacity.

Current acquisition adapter: official public npm, exact root versions, frontend package.json/package-lock.json. NuGet, Python, custom/private registries, install scripts, cross-run grant inheritance and automatic vulnerability/license certification are not implemented. They require separate controlled adapters/policies, not blanket network access. Grants are additionally run-bound; same-request cached resolution is reusable, while another run needs fresh authorization. A changed source manifest/lock after resolution fails closed and may require owner reconciliation/revised planning. Full live model/GitHub delivery certification remains separate from deterministic orchestration/browser tests and real registry/Docker verification.

Legacy custom lock graphs require owner review even when their direct package names appear in the offline catalog: every non-root catalog lock entry must match the immutable built-in graph. npm-shrinkwrap is unsupported and rejected. Repository files cannot supply the reserved trusted dependency-cache archive prefix. These checks prevent cached content or a forged transitive lock entry from conferring authorization.
